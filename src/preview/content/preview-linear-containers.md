## 两个不同层次的问题

“栈还是队列”决定允许怎样访问元素；“数组还是链表”决定元素怎样存储。把二者混在一起，会误以为栈只能放在数组里、队列只能放在链表里。

事实上，两种逻辑结构都可以有多种存储实现。

### 从使用场景判断

- 撤销最近一次编辑：优先考虑栈。
- 按到达顺序处理任务：优先考虑队列。
- 需要按下标随机访问：单纯的栈、队列接口通常不合适。

## 看清标准库接口

```cpp
std::stack<int> undo;
undo.push(1);
int newest = undo.top();
undo.pop();

std::queue<int> waiting;
waiting.push(1);
int oldest = waiting.front();
waiting.pop();
```

实际使用前需要包含 `<stack>`、`<queue>`，并确保读取或删除时容器非空。上面的 `pop()` 不返回被删除的元素；先读取，再移除。

### 复杂度与实现前提

接口名字本身不是复杂度证明。讨论数组实现时，需要说明是否允许扩容、是否搬移元素；讨论链表实现时，需要说明有没有尾指针，以及是否已经拿到需要操作的节点。

## 给自己的检查清单

1. 数据按什么顺序进入和离开？
2. 需要访问中间元素吗？
3. 容量有没有上限？
4. 当前操作是否满足非空等前提？

## 从撤销与任务调度比较需求

撤销操作关注最近一次尚未撤销的动作，任务调度则可能关注最先到达且尚未处理的任务。二者都可以抽象成“保存一些工作”，但删除策略不同。若强行用同一个接口掩盖这种不同，调用者就只能通过约定记住哪些操作可以做，错误会更隐蔽。

### 接口越多并不一定越灵活

假设业务只需要先进先出，暴露随机下标修改可能让调用者绕过顺序约束。数据结构的接口也是一种约束表达：只开放队首读取和队尾写入，能够直接阻止一部分非法操作。需要检查中间任务时，也可以设计专门的只读查询，而不是开放所有内部存储。

## 数组与链表的实际取舍

连续数组便于顺序读取，但扩容可能搬移已有元素；链表节点位置分散，每个节点还需要链接信息。这里不能仅凭“插入是常数时间”就宣布链表一定更快，因为还要说明插入位置是否已知、是否需要查找，以及分配器的成本。

| 问题 | 数组实现需要检查 | 链式实现需要检查 |
| --- | --- | --- |
| 容量增长 | 扩容策略与搬移 | 节点分配是否失败 |
| 删除队首 | 是否整体搬移 | 头指针与空表更新 |
| 插入队尾 | 剩余空间 | 是否维护尾指针 |
| 遍历 | 有效长度和循环位置 | 结束条件与断链 |

### 复杂度中的平均与最坏情况

动态数组追加通常讨论摊还复杂度，一次扩容仍然可能很贵。如果应用有严格的延迟限制，就不能只看许多操作的平均成本。固定容量队列避免了扩容，却需要定义队列满时的行为：拒绝新任务、丢弃旧任务或等待，都不是可以偷偷决定的细节。

## 把错误状态写进接口

返回一个普通整数无法同时清楚表达“弹出了零”和“没有元素”。可以返回可选值，也可以通过返回布尔值与输出参数分开表达。选择哪一种并不重要，重要的是调用者必须有办法区分状态，且不会因为忘记判断而读取一个无效结果。

```cpp
#include <queue>
#include <optional>
std::optional<int> takeNext(std::queue<int>& jobs) {
    if (jobs.empty()) return std::nullopt;
    int value = jobs.front();
    jobs.pop();
    return value;
}
```

### 所有权与生命周期

队列里保存值、指针或引用，意味着不同的生命周期责任。保存指针不会自动延长对象寿命。任务对象在入队后被别处销毁，队列仍然非空，但队首已经不能安全访问。讨论接口正确性时，需要同时写清谁创建对象、谁最终释放对象，以及处理期间谁能修改它。

## 一个完整的设计练习

给打印服务设计等待队列时，我会先列出需求：按提交顺序处理；允许取消尚未开始的任务；限制总容量；失败后可以重试。接着发现，普通队列的接口不足以高效定位任意待取消任务。此时应该重新设计，而不是为了保住“这是一个队列”而扫描所有元素、绕过所有约定。

结构的名字只是起点。真正的设计结果是一组可以解释、可以测试的行为，包括空、满、取消、失败和重复提交。把这些行为写清楚后，选择存储实现才有可比较的依据。
