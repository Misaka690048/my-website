## 先把现象说清楚

“页面不正常”很难成为排错的起点。我更愿意写下操作顺序、预期结果和实际结果。例如：打开文章列表，选两个标签，进入第二篇文章，再点击返回；预期保留两个标签，实际只剩一个。这样的描述已经包含了状态变化，也方便别人照着重做。

截图能够说明结果，却未必说明到达结果的路径。对于偶发问题，还要记录是否刚刷新、是否从其他页面进入、窗口宽度以及是否启用了系统减少动画。记录的目的不是收集越多越好，而是保留可能改变行为的条件。

### 一次只改变一件事

如果同时改事件绑定、样式和数据，很容易在问题消失后不知道是哪一步起作用。我会先固定输入和路径，再改最可疑的一处。即便修改方向是错的，也能从结果中得到更明确的信息。

## 把问题缩小

一个复杂列表可能包含动画、筛选、路由和共享元素过渡。先暂时关闭动画，如果状态仍然错误，就应优先检查数据与 URL；如果状态正确但视觉错位，再查看布局与动画快照。不同层次的问题需要不同的观察手段，不能只靠在同一处反复调数值。

### 可观察的证据

日志最好记录事件发生的顺序以及关键状态，而不是到处输出“运行到这里”。例如使用以下结构，能够对照一次操作前后的标签变化。

```json
{
  "event": "filter-change",
  "before": ["编程实践"],
  "after": ["编程实践", "边界与测试"],
  "visibleCount": 2
}
```

测试日志不应包含账号令牌、私人正文或无关的个人信息。将复现样例替换成简单的虚构内容，通常既方便分享，也能减少噪声。

## 假设需要能被推翻

“可能是缓存”不是一个足够完整的假设。应继续写：如果是缓存导致，那么绕过缓存后同一输入应得到不同结果；如果没有变化，就需要寻找别的解释。这样每次操作都有判定标准，不会在刷新、重启和清理之间无限循环。

| 假设 | 观察方法 | 反例意味着什么 |
| --- | --- | --- |
| 数据没有更新 | 检查实际响应内容 | 响应已新则查渲染 |
| 监听器重复绑定 | 记录一次点击触发次数 | 只触发一次则另查 |
| 布局尺寸变化 | 比较换页前后元素尺寸 | 尺寸一致则查动画 |

### 最小复现并不一定最短

复现代码可以删掉无关部分，但不能删掉触发错误的顺序。有的缺陷只在第二次访问后出现，简化成首次加载反而会把问题消掉。一个保留必要状态、别人能稳定运行的例子，比一个非常短却不再出错的例子更有价值。

## 修改后的验证

修复之后先重走原来的失败路径，确认问题消失。然后测试邻近情况：没有标签、一个标签、没有匹配结果，以及用浏览器后退而不是页面返回链接。这些场景围绕同一状态边界，比无目的地点击所有页面更有效。

### 别让测试只复述实现

如果代码使用了某个固定阈值，测试不应只断言变量等于这个阈值，而应观察边界两侧的实际行为。同样，日期测试应包含跨时区午夜，而不是只检查一个下午的日期。好的测试会在实现被错误改动时失败，而不是只证明测试作者看过源码。

## 留下一份短记录

最后记录触发条件、原因、修改和验证范围。若没有做手机实测，就写没有做；若只是从源码推断，就不要写成已在浏览器观察到。这样下一次遇到相似问题时，可以迅速判断旧结论适用到哪里。

排错的收获并非每次都找到一个复杂原因。有时只是两个容器的行高不同，或一个事件比预期早执行。重要的是从现象到结论之间有一条可以复查的路径，而不只是“改完好像好了”。
